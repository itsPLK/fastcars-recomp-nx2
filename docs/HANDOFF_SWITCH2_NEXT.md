## 1. Root causes found and fixed on `hydrogen`

### A. Boot 7 crash (`SetInterruptCallback` → `std::system_error`)
- **Cause:** `std::thread::detach()` calls `pthread_detach()`, which returned `ENOSYS` in `libounce`, throwing an uncaught `std::system_error` → `std::terminate()` → `abort()` → `_exit()`.
- **Fix (commit `33cbec5`):** Added [`switch2/support/pthread_detach.c`](../switch2/support/pthread_detach.c) (`__wrap_pthread_detach` returning `0`) and `-Wl,--wrap=pthread_detach` in [`switch2/support/CMakeLists.txt`](../switch2/support/CMakeLists.txt).

### B. Boot 9/10 crash (null audio render driver vtable call)
- **Cause:** `NopAudioSystem::CreateDriver()` returned `X_STATUS_NOT_IMPLEMENTED`, leaving the game's client audio render driver pointer null (`r3=0x00000000`, `lr=0x837A8510`).
- **Fix (commit `33cbec5`, `rexglue-sdk` commit `99bed782`):** Implemented `NopAudioDriver` with a 5 ms `std::thread` pacer releasing the client semaphore and joining on destruction in [`rexglue-sdk/src/audio/nop/nop_audio_system.cpp`](../rexglue-sdk/src/audio/nop/nop_audio_system.cpp).

### C. Swapchain format (`R8G8B8A8_UNORM`)
- **Fix (commit `be3a69c`):** Switched the swapchain format / presentation path on Switch 2 to `R8G8B8A8_UNORM` and restored `--log_level=info` in [`switch2/game/args.txt`](../switch2/game/args.txt).

### D. Severe triangle-edge & shared-diagonal pixel dropouts across the whole game
- **Symptom:** Both 2D UI/loading screen quads and 3D meshes showed 2–16 px notches and slits along triangle edges and even along the shared interior diagonal of two-triangle quads (`IMG_8565`, `IMG_8568`, `IMG_8570`).
- **Hardware bisection on Switch 2 (all verified via `fastcars-display-test.nro` and `fastcars.nro`):**
  1. **Geometry shaders ruled out:** `--fastcars_native_rect_gs=false` (`RectExpand` CPU path) showed identical notches on both 2D and 3D draws.
  2. **Rasterization / `plume` swapchain ruled out:** Raw `plume` + simple GLSL SPIR-V in `switch2/display-test/main.cpp` drew 4 colored 2-triangle rectangles over green with zero notches (even with negative viewports, `depthClipEnabled=false`, `dynamicDepthBiasEnabled=true`).
  3. **Vertex shaders / geometry / render passes ruled out:** Booting real `fastcars.nro` with `--fastcars_native_diag_all=3` (`PSDiagFlat` replacing every guest pixel shader while keeping all the game vertex shaders, buffers, `RectExpand`, offscreen targets, and barriers) rendered every triangle edge and shared diagonal razor-sharp.
  4. **Exact pixel-shader trigger isolated (`OpKill` / `discard`):** Every `XenosRecomp` pixel shader emits `[branch] if (g_AlphaToMask != 0) clip(...)` (`OpKill` loaded via `PhysicalStorageBuffer64`), so Mesa NIR keeps `uses_discard: true` and lowers to `@demote_if` → `@p0 kill` even when `g_AlphaToMask == 0` at runtime. In a 4-quadrant `fastcars-display-test.nro` test:
     - `ps_7E3B3A8FFA03E5D6.spv` untouched (`uses_discard: true`, runtime branch false) → **notches**.
     - `ps_7E3B3A8FFA03E5D6.spv` with its two `OpKill` terminators patched to `OpBranch` → **clean**.
     - Simple GLSL PS with `oC0.a = 1.0` (NIR constant-folds `1.0 < 1.0 - ...` to false and eliminates `kill`) → **clean**.
     - Identical GLSL PS with `oC0.a = 0.5` (NIR keeps `@p0 kill` inside `if (atm != 0u)` even with `atm == 0`) → **notches**.
  5. **Driver root cause isolated (`NAK_DEBUG=nougpr`):** Testing `NVK_DEBUG=no_compression,no_cbuf,no_sector_promotion` + `NAK_DEBUG=nougpr` cured all 4 `OpKill` shaders. Bisecting showed `NVK_DEBUG=no_compression` alone still failed (`all look bad`), while **`NAK_DEBUG=nougpr` alone** made all 4 `OpKill` shaders **100% clean**.
     - Inspection of `NAK_DEBUG=print` output showed Mesa 26.2.2 NVK/NAK (`0x808`) promoting uniform values (`r2ur` → `ur*`, `up0 = isetp ...`, `bra !up0`) in `uses_discard: true` shaders (`SPH` `kills_pixels` set) alongside warp edge helper invocations. Disabling UGPR promotion (`NAK_DEBUG=nougpr`) eliminates the miscompilation without disabling any guest `clip`/`OpKill` behavior (needed for foliage, fences, alpha-tested UI, and alpha-to-mask).
- **Fix in [`fastcars/src/native/renderer.cpp`](../fastcars/src/native/renderer.cpp):**
  - Under `#elif defined(__SWITCH__)`, sets `setenv("NAK_DEBUG", "nougpr", 0);` at static initialization before any Vulkan device exists (`0` lets an explicit `NAK_DEBUG` override win).
  - Switches `Renderer::PipelineCachePath()` on `__SWITCH__` to `shader_cache/vk_pipelines_nougpr.bin` so pre-fix `vk_pipelines.bin` caches cannot reintroduce UGPR shaders after an upgrade.
- **Verified on Switch 2 hardware:** Uploaded fixed `fastcars.nro` (with `--fastcars_native_rect_gs=false` removed and stale `sdmc:/config/ouncevk/shader-cache/` + `sdmc:/fastcars/shader_cache/vk_pipelines.bin` deleted); user verified clean rendering across loading screen / gameplay.

### E. Audio (native `audout` backend)
- `rexglue-sdk/src/audio/switch2/switch2_audio_system.cpp` (SDK `c40758b5`): guest 5.1 frames folded to stereo s16, one 256-sample frame per 4 KiB `audout` buffer, 3 queued (~16 ms); each frame handed to the device releases the client semaphore (the device clock paces the guest audio engine). Falls back to silent 5.3 ms pacing if `audout` fails. Log: `audio: N of 1875 frames were silence` every ~10 s (0 in gameplay on hardware).

### F. Clocks: do NOT raise EMC in handheld (CPU halves)
- `fastcars/src/switch2_clocks.cpp` logs CPU/GPU/EMC at startup and, every 5 s, the rates plus SoC/PCB temperature (`tsOpenSession`; `tsGetTemperatureMilliC` reads 0 on Switch 2) and every 30 s a **measured** CPU speed (16 dependent adds per iteration timed by `svcGetInfo(InfoType_ThreadTickCount)`, i.e. the thread's own run time).
- Handheld stock on this console: CPU 1100, GPU 561, EMC 2133 MHz (possible ranges: CPU 115-1702, GPU 306-1389, EMC 204-3750).
- **Finding (2026-11-14):** `--switch2_clocks=0,1007,3200` (GPU + EMC to docked retail rates, in handheld) was accepted (rc 0, rates read back as set, no drift) but gameplay fell from ~30 fps to ~12: renderer recording 18 -> 40 ms, GPU frame 25 -> 29-47 ms. The measured CPU speed was **548 MHz** while clkrst still reported 1100. With GPU back at 561 but EMC still 3200 it stayed at 548; with EMC back at 2133 it measured 1093 and the game was back at ~30 fps. So the firmware's handheld power budget throttles the CPU in hardware when EMC is raised, and clkrst does not show it.
- **clkrst rates persist after the process exits** (and survived launching/closing a retail game). `switch2/clock-reset/` builds `clock-reset.nro` (A = handheld stock 1100/561/2133, X = docked stock 1100/1007/3200). `--switch2_clocks` defaults to `keep` and `args.txt` no longer sets it.
- **CPU alone to 1702 (snaps to 1689) holds: measured ~1686 MHz**, recording 22 -> 10 ms, gameplay ~46 -> ~30 ms/frame (35-40 fps); now GPU-bound (GPU frame ~26 ms, ~1 ms idle). This is what `args.txt` sets.
- **CPU 1702 + GPU 1007 (EMC stock): CPU measured ~840 MHz** (halved again) and the GPU frame only went 25-28 -> 22-27 ms, so the GPU frame is not clock-bound (bandwidth/stalls, or hidden GPU throttling too). ~22 fps. GPU 768 (snaps to 777) + CPU 1702 also measured the CPU at 840: any GPU/EMC raise above the handheld rates puts the CPU at exactly half its set rate (a throttle mode, not a sliding budget), so there is no in-between. Untested: anything docked. Check the measured CPU line after any clock change.

### G. Exit
- (Removed: quitting is HOME -> Close only, see section 5, item 5.) Was: hold **[-] + [+]** for 0.5 s: `ProcessQuitRequest()` from the Switch 2 main loop (`rexglue-sdk/src/ui/windowed_app_context_switch2.cpp`, SDK `fed05403`), the same path as the system exit request.
